# Version 0

This version is for a simple fastapi backend with the following functionality:

1. A health check endpoint (/health)
2. An endpoint (/essay/judge) where someone can submit an essay as a simple json structure with a idempotency_key, essay_id, title and body and sources. The sources field and essay id field is optional for now and will simply be discarded if provided. The endpoint returns a json in the rough following format:

{
    isValid: True/False,
    length: {isValid: True/False,
             rationale: str
        },
    density: {isValid: True/False,
             rationale: str
        },
    logical_validity: {isValid: True/False,
             rationale: str
        },
    sources: // Always empty for now
    essay_id: //Always empty for now
    idempotency_key: // Autogenerated in input to prevent duplicate hits

}

It must be compilable and runnable as a docker image

## Version 0.1

For an essay that is passed, it is saved to a backend PostgreSQL service.  

So, we will need the following new functionality:
1. Configuration env variables for PostgreSQL db
2. Services interacting with the db using those env variables and being able to succesfully read and interact with tables
3. Local development must spin up a local DB such that make dev creates a functional local version of the product.
4. Input essay ids must either be NULL or point to an existing essay in the db.
5. The DB must store essays with versioning. In case of conflicts, use optimistic concurrency (first one to increase the version wins). 
6. The DB stores all derived information about quality in a retrievable way
7. The fastAPI service has new endpoints:
    * /essay/submit that is used to submit a new essay or a new version
    * /essay/get that is used to get a stored essay. If there are multiple versions, the latest is grabbed by default. Or, a specific version can be requested. 

This document will be updated with future milestones as the existing ones are finished.
